# The Agent Harness Hackathon — Official Rules

> **Event:** The Agent Harness Hackathon (WeMakeDevs × TrueFoundry × Qodo × OpenAI)
> **Window:** 24 August, 8:00 AM London → **30 August, 8:00 PM London** (submission close)
> **Captured:** 24 August 2026 · Source: official rules page, pasted verbatim by participant
> **Status:** Binding. Registering means agreeing to all of these plus the WeMakeDevs Code of Conduct.

---

## 1. Participation Basics

| Rule | Detail |
|------|--------|
| Format | Fully online from anywhere; entry is free |
| In-person option | San Francisco live-build day on 29 August — requires separate Luma registration, limited space |
| Team size | Solo, or a team of up to **4** members |
| Exclusivity | Each participant may belong to **one team only** |

**Live-day perk:** everyone who attends in person receives $50 in OpenAI credits. Online participants bring their own model API key.

## 2. Required Technology (Rule 3 — the qualifying rule)

- The agent **must run on TrueForge**, the open-source agent harness.
- A judge must be able to **see the harness doing real work** — reaching tools, executing code in a sandbox, pausing for approval — *not* sitting under a thin wrapper around a raw model call.
- Everything else (domain, stack, tooling) is deliberately open-ended.

## 3. Originality & Timing

- All coding and design work must happen **inside the hackathon window** (after 24 Aug, 8:00 AM London).
- Pre-work allowed: discussing ideas, taking notes, planning architecture, preparing diagrams.
- Frameworks, open-source libraries, public APIs, templates, third-party tools, and publicly available assets are all permitted — the **original work completed during the week** is what gets judged.
- The project must be **built during the hackathon**; pre-existing codebases are out of scope.

## 4. Data & Permissions (Rule 6)

- Anything the agent touches must be **yours to touch**: your accounts, your data, your tools — or things you have explicit permission to use.
- Private, personal, and login-protected information stays **out of the repository and out of the demo video**.

## 5. Mandatory Deliverables (Rule 9)

1. **Public source-code repository**
2. **README** with clear setup steps a stranger can follow
3. **Demo video** (~3 minutes) showing the agent working
4. **Short write-up** describing what the agent does and how it uses TrueForge
5. **Blog post link** — only if entering the blog prize track

## 6. AI Assistance & Participant Understanding (Rules 11–13 — critical)

| Rule | Obligation |
|------|-----------|
| 11 | AI coding assistants are **allowed but their use must be disclosed** |
| 12 | Participants must genuinely **understand the submitted code** and be able to explain the agent, the architecture, and the technical decisions behind them |
| 13 | Projects **entirely generated by AI** without meaningful participant contribution, verification, or technical understanding **may be rejected** |

> **Implication:** this is a pair-programming engagement by design. Every architectural decision gets explained; every module gets walked through; disclosure of assistant usage goes into the README/write-up.

## 7. Tracks & Prizes (Rule 14)

Three judged tracks. Every submission is considered for all three, but one team wins at most one.

| Track | Prize | Special condition |
|-------|-------|-------------------|
| Best Use of TrueForge | One team prize | Harness visibly central, not decorative |
| Best Code Quality | One team prize | **Running pull requests through Qodo is required to win** |
| Best UI | iPad for **every member** | Judged on presentation/interface |

Additional opportunities:

- **Blog post prize** — one writer; publish anywhere, link it in the submission.
- **Swag** — ten participants who share builds publicly tagging WeMakeDevs and TrueFoundry.
- **Interviews** — TrueFoundry offers job interviews to teams behind top projects (independent of winning a track).

## 8. Conduct, IP, Enforcement (Rules 17–20)

- IP created during the hackathon belongs to the participants/team that created it; teams should agree on ownership internally before submitting.
- Respect all participants, organisers, sponsors, speakers, judges, and community members.
- Harassment, discrimination, plagiarism, or judging manipulation → disqualification.
- Any breach of these rules or the Code of Conduct may result in disqualification.

## What This Means for Us (working notes)

1. **Workflow is dictated by the Code Quality track:** install Qodo on day one, branch → pull request → review → fix → merge, from the very first commit. No commits straight to main. The PR history *is* the evidence.
2. **The approval gate must appear in the demo video** — it is an explicit judging criterion ("Control and Safety") and the thing nobody usually films.
3. **Disclosure obligation:** our README and write-up will state plainly that an AI pair-programmer (Claude Code) was used, per Rule 11.
4. **Understanding is a pass/fail risk:** every component will be built with explanation-first walkthroughs so the participant can defend any line in a judge interview.
5. **Scope discipline:** one narrow job finished end-to-end beats a platform with half-finished breadth — reinforced by both the best-practices page and the 3-minute demo format.
